# Work Ease Develop

Use this skill for Work Ease behavior-tree-like task orchestration and the C++ task layer that exposes robot actions/checks to scripts.

## Workflow

1. Identify whether the request is about script authoring, C++ task implementation, task registration, script interpretation, or runtime behavior.
2. Read `references/work_ease_reference.md` for syntax and semantic rules before generating non-trivial scripts.
3. For detailed examples, load only the matching source tutorial in `references/work_ease_docs/`.
4. Keep generated C++ aligned with the current repository style and embedded constraints: predictable runtime, minimal allocation on hot paths, explicit lifecycle handling, concise logs.

## Core Model

- A script runs task instances and task groups in sequence unless a control node changes that behavior.
- `var name = TaskType("task_name")` declares a task instance; `TaskType` must be registered in C++.
- Custom tasks usually inherit `we::task::SyncTask` for running actions or `we::task::SyncRequestTask` for immediate checks.
- Register C++ task types with `REGISTER_TASK_TYPE(TaskClass)` after including `types/reflex.h`.
- Interpret inline script with `ScriptInterpreter::interpret(code)` or file script with `ScriptInterpreter::interpretSourceFile(path)`.
- On parse failure, return or print `ScriptInterpreter::getErrorInfo()` with line, column, line code, and message.

## Script Rules

- One statement per line.
- Group bodies must always use `{}` even for one statement.
- Comments start with `#`.
- String literals use double quotes.
- Boolean operators are `!`, `and`, and `or`.
- Sequential execution stops when a task or group fails unless wrapped by a control node such as `force_pass`.

## Control Node Selection

- Use `if/else` for one-shot branching.
- Use `while(condition)` when the condition should be checked between complete body executions.
- Use `reactive(condition)` when the condition must be checked continuously while the body is running.
- Use `repeat(n)` to run a body up to `n` times and stop on first failure.
- Use `retry(n)` to retry a body after failure and stop on first success.
- Use `parallel` when multiple tasks should tick together; all must succeed, and failures halt remaining running tasks.
- Use `force_pass` when cleanup or fallback work should allow the enclosing flow to continue.
- Use `force_fail` when a body should always report failure after executing.
- Use `function name()` to package reusable script logic; define before use.
- Use `import path` to load task instances and functions from another script; imported top-level execution logic is not imported.

## C++ Task Guidance

- The Task constructor will be invoked when parsing the script. Its destructor runs when the schduler generated by script parsing is destructed.
- Implement lifecycle callbacks intentionally: `onStart`, `onRunning`, `onPause`, `onResume`, `onCancel`, `onHalt`, and `onReactive` when relevant.
- Return `we::task::Running` while asynchronous work is incomplete, then `Success` or `Failure`.
- `reactive` failure triggers child `onReactive()`: return `true` to ignore that reactive event and continue ticking; return `false` to halt and report failure.
- `parallel` failure triggers `onHalt()` on remaining running children.
- Avoid local ROS publisher/subscriber lifetimes for task callbacks; store them as members where ROS communication must persist.
